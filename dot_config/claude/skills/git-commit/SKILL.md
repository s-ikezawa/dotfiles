# コミット

コミットログは、後でこのリポジトリを触るAIや人が「なぜこうなっているか」を知るための、ほぼ唯一の記録。
会話は消えるが、ログはコードと一緒に残る。後で読むAIは差分を読めるが、差分に無いことは何も知らず、
会話も知らない。その読み手が判断に使えることを書く。

## 読み手はどう読むか

書き方はこの読まれ方で決まる。

- `git log --oneline`・`git blame`・コミットグラフでは件名しか見えない。件名で当たりを付けてから
  `git show` で本文を読む。
  → 件名は単独で意味が通り、どの機能・ツールの何のための変更かが分かるようにする。
- `git log --grep` や `git log -S`（コードの文字列）で探す。grep は行ごとに照合する。
  → 探されそうな語（ツール名・設定キー・関数名・エラーメッセージ）を、コードやログと同じ表記で書く。
  訳したり言い換えたりしない。
  → 本文の折り返しで語句やエラーメッセージを分断しない。日本語は句読点の後で折り返す。
- 書いてあることは事実として扱われる。AI はたいてい確かめずに前提にする。
  → 確かめていないことを断定しない。推測なら推測と書く。理由が分からないなら作らずに聞く。

## 本文に書くこと（差分から復元できないもの）

差分を読んでも分からないことだけを書く。当てはまるものだけでよい。

1. 動機: 何に困っていたか。症状、エラーメッセージ（そのまま）、起きる条件。
2. 原因: 分かっていれば。どのツールのどのバージョンのどの挙動か。
3. 捨てた案: ほかに試した・考えた方法と、だめだった理由
   （無いと、後の AI が「もっと簡単な方法がある」と捨てた案へ戻してしまう）。
4. 見た目に反する部分: 一見いらない・遠回りに見えるが必要なもの。消すと何が壊れるか。
5. 外す条件: 一時的な回避策なら、何が起きたら戻せるか（例: v3.0.0 が出たら、upstream の #123 が閉じたら）。
6. 確かめ方: 動作をどう確認したか（コマンドや手順）。
7. 範囲: わざとやらなかったこと、分かっている制限。
8. 参照: Issue・PR の番号、upstream のコミット、関係する過去のコミットのハッシュ。
   リンク先が読めなくなっても困らないよう、要点は本文に書き、リンクは補足にする。

## 書かないこと

- 差分の言い直し（「A を B に変更」「X を追加」）。差分を読めば分かり、読み手のコンテキストを無駄に使う。
  ただし大きな機械的変更は「名前の置き換えだけで動作は変わらない」と書く（差分を読み飛ばせる）。
- 会話の中でしか通じない言葉（「さっきの」「ユーザーの要望で」「例の不具合」「前のコミット」）。
  ハッシュ・バージョン・日付・具体的な症状で書く。
- 中身の無い語だけの件名（「修正」「改善」「対応」「調整」「いろいろ」）。何をどう直したかを書く。
- 相対的な時間（「最近」「今のところ」）。日付かバージョンで書く。
- 作った理由や、確かめていない因果関係。
- シークレットや個人情報。

## 件名

- リポジトリの既存の書き方（言語・prefix・形式）に合わせる。決まりが無ければ「〜するため、〜する」の
  ように目的と変更を 1 行に書く。
- 目的は「何が良くなるか」を観察できる形で書く（「〜が古いまま残るのを直すため」）。
- 対象の名前（ツール名・機能名）を入れる。パスより名前のほうが探しやすい。
- 1 行に収まらないほど言いたいことが多いなら、コミットが大きすぎる疑いがある。

## 本文の長さ

自明でないほど長くする。理由が件名で言い尽くせているなら件名だけでよい。回避策・捨てた案・
直感に反する変更は長くなってよい。足りているかは、後で blame した AI が「この行を消していいか」
「なぜこの方法なのか」に答えられるかで判断する。

## コミットの単位

- 1 コミット 1 目的。整形やリネームと動作の変更は分ける（blame・revert・bisect が 1 つの理由を指すように）。
- 確かめられる単位で区切る。
- 混ざっていたら、分け方をユーザーに提案する。

## コードのコメントとの使い分け

コミットメッセージは「そのとき、なぜ変えたか」の記録で、後の変更で blame から外れると辿りにくくなる。
今のコードを触る人が毎回知るべき制約（消すと壊れる、ここだけ順番が大事）はコードのコメントにも
短く書き、詳しい経緯はコミットに書く。

## 手順

1. `git status` と `git diff --staged`（何もステージしていなければ `git diff`）で変更を見る。
2. `git log -15 --format='%h %s%n%b---'` で既存の書き方（言語・prefix・本文の量・トレーラー）を見る。
3. 変更が 1 つの目的か確かめる。混ざっていれば、分けるかユーザーに聞く。
4. 理由を会話・Issue・調べた結果から集める。動機が分からなければ、作らずにユーザーに聞く。
5. メッセージを Write ツールで一時ファイル（スクラッチパッド、なければ `$TMPDIR`）に書く。
6. 対象のファイルを `git add <パス>` で明示して加え（`-A` や `.` で関係ないファイルを入れない）、
   `git commit -F <一時ファイル>` でコミットする。
7. フックで止まったら `--no-verify` で飛ばさず、原因をユーザーに報告する。
8. `git log -1 --stat` で結果を確かめる。push は頼まれたときだけ。

トレーラー（`Co-Authored-By` など）は、リポジトリの慣習とシステムの指示に従う。

## 書いたら確かめる

- 件名だけで、どの機能の何のための変更か分かるか。
- 会話を知らない人が本文だけで理解できるか。
- 書いた理由はすべて、確かめたことかユーザーが言ったことか。
- 後で探すときの語（ツール名・設定キー・エラー文）が、コードと同じ表記で入っているか。
- 差分の言い直しになっていないか。

## 例

悪い例（何のためか分からず、会話を知らないと読めない）:

```
gitsignsの設定を修正

gitsignsのブランチをmainに変更しました。
ユーザーの要望で、さっきの不具合を直すためです。
```

良い例（症状・原因・根拠・外す条件がある）:

```
外でコミットしてもgitsignsの印が古いまま残るのを直すため、v3.0.0が出るまでmainを追う

v2.1.0は.gitを見張るハンドルの後片付けをGCに任せていて、
見張りだけ止まったリポジトリの情報が使い回されることがある。
修正（c5480c0・1189caf）はmainにだけ入っている。
v3.0.0が出たらタグの指定に戻す。
```

良い例（捨てた案と確かめ方がある）:

```
CIのテストがたまに落ちるのを止めるため、DBを使うテストを直列に実行する

並列だと同じテスト用DBのテーブルをTRUNCATEし合い、
10回に1回ほど relation "users" does not exist で落ちていた。
テストごとにスキーマを分ける案は、マイグレーションに30秒かかって全体が3倍遅くなるため見送った。
確認: go test -count=20 ./internal/db/... が20回とも通る。
```
