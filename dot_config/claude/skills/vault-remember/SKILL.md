# Vault に書き残す

Vault は `~/Projects/github.com/s-ikezawa/obsidian-vault` にある（なければ `ghq list -p | rg obsidian-vault`）。
ノートの書き方（フォルダ・type・ファイル名・frontmatter・リンク・書いてはいけないもの）は、
リポジトリのルートの `AGENTS.md` に従う。**書く前に必ず `AGENTS.md` を読む**（このファイルには写さない）。

## 何を残すか

後で別の作業をするとき、知っていれば時間を節約できたり、間違いを避けられたりすることだけを残す。

| 残すもの | type | 置き場所 |
|---|---|---|
| 手順・使い方 | `How-to` | `vault/notes/` |
| エラーの症状・原因・解決 | `Troubleshooting` | `vault/notes/` |
| 仕組み・用語の理解 | `Concept` | `vault/notes/` |
| 調査・比較と結論 | `Research` | `vault/notes/` |
| AI や人のミス・再発防止のルール | `Mistake` | `vault/notes/` |
| プロジェクトの設計判断と理由 | `Decision` | `vault/projects/<リポジトリ名>/` |

残さないもの:
- 作業の経緯そのもの（何をどの順にやったか）。作業したリポジトリの git log や PR に残る。
- そのリポジトリのコードや README を読めば分かること。
- シークレットや社外秘の内容（`AGENTS.md` の「書いてはいけないもの」）。

## いつ書くか

- **「覚えておいて」と言われたとき:** その内容を書く。
- **作業の区切り（問題が解決した・判断が決まった・ミスを直した）:** 自分からは書かず、
  「Vault に残すと良さそうなもの」を 1〜3 件、type とタイトル案付きで挙げてユーザーに聞く。
  ユーザーが選んだものだけを書く。

## 手順

1. `AGENTS.md` を読む。
2. **同じ内容のノートがないか探す**（探し方は `vault-recall` Skill と同じ。`index.md` → frontmatter の `rg`）。
   あれば新しく作らず、そのノートを更新する（`generated` を書き換え、`verified` は消さない）。
3. `vault/templates/<type>.md` に沿って書く。
   - 作業中のリポジトリでしか通じない言葉（ファイルのパス・社内の名前）は、他の作業でも分かる言い方にする。
   - 確かめた範囲を正直に書く（`AGENTS.md` の「確かさの記録」）。この作業で実際に動かして確かめたら
     `stable` と `verified`、推測を含めば `draft`。確かめた環境（バージョン・OS）を本文に書く。
   - `Decision` で、そのプロジェクトのフォルダがまだなければ、`Project` ノートと `index.md` も作り、
     `vault/projects/index.md` に足す。
4. リンクを書いたら、リンク先が実在するか確かめる（`AGENTS.md` の「リンク」）。
5. そのフォルダの `index.md` に `* [タイトル](相対パス) - description` を足す。
6. **`Mistake` の再発防止のルール**で、すべてのリポジトリの作業に効かせるべきものがあれば、全体の
   `CLAUDE.md` などへの反映をユーザーに提案する。勝手に反映しない。
7. 書いたノートのパスと要点を伝え、Vault のリポジトリにコミットするかをユーザーに聞く。
   コミットするなら、ノートと `index.md` を 1 つのコミットにする（`git -C <Vault> ...`）。
