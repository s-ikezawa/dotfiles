# Pull Request

マージは merge commit で行い、PR のタイトルと説明がそのまま merge commit の件名と本文になる
（GitHub のリポジトリ設定で merge_commit_title が PR_TITLE、merge_commit_message が PR_BODY）。
つまり PR の説明は GitHub 上の一時的な文章ではなく、git の履歴に残るコミットメッセージそのもの。

先に Skill ツールで `git-commit` スキルを読み、書くこと・書かないこと・件名の基準をそのまま使う。
ここには PR で違う点だけを書く。

## PR の説明とコミットの違い

- 個々のコミットは merge commit の下に残る。AI は `git log --first-parent` で merge commit を
  一覧して全体の流れを掴み、必要なものだけ `git log <merge>^1..<merge>^2` で中のコミットを読む。
  → 説明は、各コミットのメッセージの寄せ集めにしない。PR 全体の目的、コミットどうしの関係
  （どれが下準備でどれが本体か）、全体としての確かめ方を書く。個々の理由はコミットに任せる。
- 件名は GitHub が末尾に ` (#番号)` を付ける。その分短くてよい。
- 説明はマージした時点の内容で固まり、後で PR を編集しても履歴は変わらない。
  → マージ前に、説明が最終的な変更と合っているか確かめる。レビューで方針が変わったら、
  変わった後の内容と、なぜ変えたか（レビューで出た捨てた案）を説明に書き直す。
- レビューのやりとりは GitHub にしか残らない。履歴から辿れるよう、決まったことは説明に書き戻す。
- 説明は git log では Markdown として描画されず、そのまま表示される。
  → 段落と `-` の箇条書き程度にとどめる。HTML・画像・表・チェックボックス・`<details>`・
  見出しの多用は避ける。画像で見せた結果は、何が確かめられたかを文で書く。
- `@ユーザー名` は通知が飛ぶうえ、履歴では意味を持たない。書かない。

## 説明に入れず、PR のコメントに書くもの

レビューする人には必要でも、履歴には残したくないもの。PR を作った後に `gh pr comment` で書く。

- 「ここを重点的に見てほしい」などのレビューの依頼
- スクリーンショットや、作業途中のメモ
- 説明を書き直す前の古い方針（書き直した説明には、捨てた理由だけを残す）

## 手順

1. 既定のブランチにいないか確かめる。いれば、ブランチを作るかユーザーに聞く。
2. 未コミットの変更があれば、コミットするか（`git-commit` スキル）PR に含めないかを聞く。
3. `gh api repos/{owner}/{repo} --jq '{merge_commit_title, merge_commit_message, allow_merge_commit}'`
   で設定を見る。PR_TITLE・PR_BODY・true でなければ、説明が履歴に残らないことをユーザーに伝える
   （設定はユーザーに頼まれない限り変えない）。
4. `git log --format='%h %s%n%b---' <base>..HEAD` と `git diff <base>...HEAD --stat` で、
   PR に入るコミットと変更を見る。関係ないコミットが混ざっていれば、分けるかユーザーに聞く。
5. `.github/pull_request_template.md` などのテンプレートがあれば従う。ただし上の Markdown の制限と
   合わない部分（チェックボックスなど）は、残すかユーザーに聞く。
6. 理由を会話・Issue・コミットから集める。PR 全体の動機が分からなければ、作らずにユーザーに聞く。
7. 説明を Write ツールで一時ファイル（スクラッチパッド、なければ `$TMPDIR`）に書く。
8. ブランチを `git push -u origin <ブランチ>` で push し、
   `gh pr create --base <base> --title '<件名>' --body-file <一時ファイル>` で作る。
   draft・レビュアー・ラベルは頼まれたときだけ付ける。
9. 確かめきれていないところや壊れたときの影響が大きいところなど、レビューで注意して見てほしい点が
   あれば、`gh pr comment <番号> --body-file <一時ファイル>` でコメントに書く。
10. 作った PR の URL をユーザーに伝える。

書き直すときは、`gh pr view <番号> --json title,body,commits` で今の内容を見てから、
`gh pr edit <番号> --title '<件名>' --body-file <一時ファイル>` で直す。

PR の説明の末尾の署名（`Generated with Claude Code` など）は、システムの指示に従う。

## 書いたら確かめる

- `git-commit` スキルの「書いたら確かめる」をすべて満たすか。
- git log で素のテキストとして読んでも崩れないか。
- 説明が今のブランチの最終的な変更と合っているか（途中で捨てた方針が残っていないか）。
- コミットメッセージの言い直しになっていないか。

## 例

```
一覧APIが件数が多いと遅くなるのを直すため、offsetのページングをカーソル方式に変える

/api/ordersは10万件を超えるとoffsetの深いページで5秒以上かかっていた（#212）。
1つ目のコミットで並び順を(created_at, id)に固定し、2つ目でカーソルを返すようにする。
3つ目は古いoffsetパラメータを受け付けたまま非推奨の警告を返すもので、
v3でクライアントの移行が終わったら外す。

レビューで出たoffsetのままインデックスを足す案は、
深いページで読み飛ばす行数が変わらず速くならないため見送った。

確認: 20万件のテストデータで最終ページが5.2秒から40ミリ秒になった。
```
