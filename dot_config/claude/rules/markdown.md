# Markdown の書き方

markdown は CommonMark に準拠して書く。

このルールはプロジェクトをまたいで使い回す。特定のリポジトリの
ディレクトリ構成、ファイル名の規則、ツールの実行方法、設定ファイルの場所は
ここに書かない。それらはプロジェクト側の指示（`CLAUDE.md` など）が持つ。

## 書式の判定は lint が持つ

何が正しい書式かは lint の設定ファイルが唯一の定義で、このルールに散文で
書き直さない。二重に書くと必ず食い違う。

markdown を編集したら lint を通し、指摘を残したまま終えない。

## 緩めるときは設定ファイルを直す

ルールは厳しい側に倒し、運用して無理だと分かったものだけを緩める。緩和は
すべて設定ファイル側で行い、なぜ無理なのかをコメントで残す。
「このファイルだけ例外」をこのルールに書き足さない。

一文だけ外したいときに限り、lint が用意しているインラインコメントで範囲を
区切る。それも使うたびに、ルールのほうが間違っていないかを疑う。

## ファイル名とパスはコードスパンで囲む

`package.json` のようなドットを含む名前を地の文にそのまま書くと、日本語の
文章を検査する lint がそのドットを和文のピリオドとみなして落とすことがある。
エラー文言からは対処が読み取れないのでここに書く。ルールを緩めるのではなく、
バッククォートで囲んで解決する。

## リンク

ファイル間のリンクは、相対パスの通常の markdown リンクで書く。

参照形式（`[text][ref]` と、定義をファイル末尾に置く `[ref]: URL`）は使わない。
定義が末尾に集まると、出典を引用の直後に置けなくなり、読む側は本文と末尾を
往復させられる。書く側も定義の消し忘れを起こす。

`[[wikilink]]` と埋め込みの `![[embed]]` は CommonMark にない記法で、対応して
いないツールではただの角括弧付きテキストとして表示される。使わない。

## 引用と出典は別のもの

引用は「他の著作者の著作物をそのまま自分の創作物に用いること」、出典は
「引用や転載の際に元となった著作物」を指す。行為と対象の違いで、引用したら
出典を示す、という関係になる。両者を同じ意味で使わない。

出典: [引用のルールとは？引用と転載の違いや文章・画像の引用方法を解説](https://magazine.unionnet.jp/knowhow/quotation-rules/)（UnionNet Magazine、2026-09-08 参照）

### 適法な引用の要件

著作権法32条。次を全部満たさないものは引用ではない（出典は上と同じ）。

1. 引用する必然性がある
2. 主従関係が明確である。自分の文が主で、引用は補完にとどまる
3. 引用部分が明瞭に区別されている
4. 出典を明示している（著作権法48条）
5. 引用部分を改変していない。句読点や文字表記も含めて一言一句変えない

引用部分が主になったものは引用ではなく転載で、権利者の許諾が要る。

### 出典は引用の直後に置く

出典は引用部分のごく近くに明記する。**ファイル末尾にまとめない。**
末尾に送ると、どの引用に対する出典なのかが読み取れなくなり、読む側は
本文と末尾を往復させられる。

区別のしかたは長さで使い分ける。段落まるごとの引用は blockquote で区切り、
直後の行に出典を書く。文中に一節だけ引くならカギ括弧で囲み、その文が属する
段落の直後に出典を置く。どちらの場合も、地の文と引用の境目が見て分かること
が要件で、記法そのものは問われない。

```markdown
> 引用文をそのまま写す。句読点も表記も変えない。

出典: [引用のルール](https://example.com/article)（サイト名、2026-09-08 参照）
```

出典の形式は次のとおり。

- Web: `出典: [ページタイトル](URL)（サイト名、YYYY-MM-DD 参照）`
- 書籍: `出典: 著者名『書名』出版社、発行年、該当ページ`

Web に参照日を付けるのは、ページが後から書き換わったり消えたりするため。

### 参考と引用を混同しない

読んだだけで文言を写していないものは引用ではない。この場合は出典ではなく
参考として示す。参考にした資料は末尾にまとめてよい。末尾送りが問題になるの
は引用の出典だけで、対応付ける相手がいない参考文献にはその問題がない。

## 実地で確かめたことは方法と結果を分ける

文献ではなく自分で動かして確かめたことを書くときは、方法と結果を別の節にする。
IMRAD が Methods と Results を分けるのと同じ理由で、結果だけを残すと後から
確かめ直せない。引用と違って突き合わせる原文が無いので、同じ手順を踏めるか
どうかでしか担保できない。

方法には、動かした環境の版と実行の手順を書く。再現性のチェックリストは分野を
問わず環境の記載を求めていて、そこが最も落ちやすいと報告されている。版が変われば
結果も変わるので、版の無い検証結果は使えない。

結果には観測したものだけを書く。そこから考えたことは別の節に置く。IMRAD が
Results と Discussion を分ける理由で、混ぜると推論が観測の顔をして残る。

コードと出力はセットで載せる。載せるコードは実際に動かしたものにする。結果が
多いときは表にまとめる。

参考: [Artifact Review and Badging](https://www.acm.org/publications/policies/artifact-review-and-badging-current)（ACM、2026-09-10 参照）
— 再現性を repeatability、reproducibility、replicability の 3 段階に分けている。
自分で繰り返せるだけの記録と、他人が同じ結果を得られる記録は別物である。
